System Architecture

시스템 아키텍처

Cloudflare → EC2(Docker: Spring Boot · Redis · Airflow) → RDS(PostgreSQL). Airflow가 관광지 데이터를 배치로 수집하고, LLM·임베딩·카카오·공공데이터 API와 연동합니다.

트러블슈팅 1

RAG 검색·튜닝과 서버 전후처리 검증으로 할루시네이션 차단

서비스 배경

AI가 강원도 소도시 여행 코스를 추천

추천 품질이 곧 서비스 신뢰

문제 상황

N일치 코스 전체를 LLM이 한 번에 생성

없는 관광지 ID, 식당 2곳 지정 규칙 위반

판단

LLM 응답은 틀릴 수 있음

장소 선택은 LLM, 규칙은 서버에서 전후처리

추천 코스가 지켜야 할 3가지와, 이를 보장하는 로직

1실재하는 장소만

없는 장소를 추천하면 신뢰가 바로 깨짐

  • 서버RAG로 후보 검색 후 휴무·중복 제외
  • LLM후보 ID 안에서만 선택
  • 서버응답 ID가 후보 안에 있는지 검사

할루시네이션이 나올 여지 차단

2자연스러운 방문 순서

식당은 끼니 시간에, 동선은 이어지게

  • 서버식당을 점심·저녁 자리에 배치
  • LLM나머지 관광지 방문 순서 결정
  • 서버대체 시에도 거리순으로 동선 정렬

시간대가 어긋난 코스 방지

3정해진 하루 구성

하루 5곳 · 식당 2곳 · 필수 방문지 포함

  • 서버식당 수·중복·필수 방문지 검사
  • 서버위반 시 최대 2회 재요청
  • 서버그래도 실패하면 규칙 기반 대체

LLM 호출 최대 3회, 코스는 항상 반환

후보 검색 RAG 품질 튜닝 · 문서 보강

  • 소개문 대신 LLM이 분류 · 키워드 · 설명 2~3문장으로 재작성
  • 설명은 “~하기 좋다”처럼 사용자 질의 문체로 작성

자연어 질의와의 유사도 향상

후보 검색 RAG 품질 튜닝 · 2단계 top-k

  • 검색 k = 하루 슬롯 × 일수 × 5 (최대 300)
  • LLM k = 날짜별 필요 개수 + 2

검색은 recall, LLM 입력은 비용·오답 최소화

트러블슈팅 2

대중교통 경로 조회 — 카카오 API 동시 호출 제어

상황

코스 확정 시 구간마다 경로 조회

코스당 카카오 API 2~30회 호출

문제 상황

순차 호출은 느려 병렬화했더니

카카오는 호출 한도 비공개, 초과로 인한 경로 누락

판단

병렬 처리는 유지하고

동시 호출 수만 세마포어로 제한

1가상 스레드로 병렬화 도입

  • 구간마다 가상 스레드로 동시 호출
  • I/O 대기 시간을 겹쳐 응답 단축

풀 크기 제한이 없어 요청이 몰리니 한도 초과 발생

2세마포어로 동시 호출 제한

  • 가상 스레드는 풀에 담아 재사용하지 않음
  • 호출 직전 permit 획득, 동시 최대 N개로 제한

N은 품질 비교 후 결정

3지연 재시도 + permit 반납

  • 한도 초과 응답만 200 → 400ms 기다리며 최대 2회 재시도
  • 재시도도 같은 세마포어 통과

백오프로 기다리는 동안엔 permit 반납, 슬롯 점유 없음

동시 호출 5

  • 1차5건 모두 한도 초과
  • 2차200ms 뒤 함께 재시도, 또 한도 초과
  • 3차마지막 재시도에서야 성공

동시 호출 2 · 채택

  • 1차일부 요청만 한도 초과
  • 2차200ms 뒤 첫 재시도에서 성공
  • 결과누락 구간 없이 전 구간 조회

트러블슈팅 1 · 지도 조회

설계 고민: Redis 캐싱 vs 일괄 조회 + ETag

지도 내 자유로운 이동

화면 영역별로 이동할 때마다 API 요청과 쿼리가 발생

전시 데이터 특성

전시 상태는 스케줄링으로 갱신. 낮 동안에는 데이터 변동 없음

목표

지도 이동마다 발생하는 무분별한 쿼리 방지

방식지도 이동 시 서버 요청비용판단
영역별 조회이동할 때마다 쿼리 발생구현은 단순하나 무분별한 쿼리 발생조건 불충족
Redis Cache-AsideAPI 요청 수는 그대로지만, 쿼리 발생 최소화모든 쓰기 경로에서 캐시 무효화 관리 필요정합성 이슈 (불일치 리스크)
일괄 조회 + ETag진입 시 1회, 데이터 변경 없으면 304한 번의 쿼리가 무거워짐채택

선택 이유

데이터 변경 주기가 일 1회로 명확하여, Cache-Aside 없이 데이터 정확성 확보 및 네트워크 대역폭 감소

ETag 동작

버전을 비교해 같으면 쿼리 없이 본문 없는 304 반환

Payload 데이터 전송량 절감

트러블슈팅 2 · 알림 발송

설계 고민: 재시도 보강 vs Outbox 패턴

기존 구조

비즈니스 데이터 커밋 후 AFTER_COMMIT 리스너가 FCM 비동기 발송, 실패 콜백은 log.warn 후 종료

문제 상황

발송 실패가 어디에도 기록되지 않음

누구에게 안 갔는지 찾을 수 없고, 재시도 또한 불가

목표

커밋됐다면 알림은 최소 한 번 반드시 발송

방식실패 건 추적 · 복구비용판단
기존 + @Retryable재시도만 될 뿐 기록 없음없음데이터 유실에 취약
Outbox + CDC (Debezium)DB 행으로 남아 조회 · 재처리 가능Debezium · Kafka모놀리식 규모 대비 과함
Outbox + 즉시 발송 · 폴링DB 행으로 남아 조회 · 재처리 가능테이블 1개채택

선택 이유

예정된 알림을 기록하여 유실 방지

  • 공지 등록 등 비즈니스 데이터와 “보낼 알림”(outbox)을 한 트랜잭션에 저장
  • 둘 다 저장되거나 둘 다 취소 → 공지 저장 시 그로 인해 발생하는 알림 유실 방지

발송 구조

두 스레드가 나눠 맡는다

  • 즉시 발송 스레드 (@Async): 커밋 직후 바로 발송 → 지연 없음
  • 폴러 스레드 (@Scheduled, 1분): 실패 · 중단 건을 회수해 재시도 (백오프, 최대 5회)
  • 두 스레드는 서로를 모른 채 따로 동작

남은 과제

즉시 발송과 폴러가 같은 알림을 겹치게 보낼 수 있다

  • 즉시 발송이 아직 보내는 중이라 행은 그대로 PENDING
  • 마침 폴러 주기가 오면 실패 건인 줄 알고 같은 행을 또 발송

같은 알림 2번 발송, 선점(claim) 필요
